# 4. การปรับความสัมพันธ์ระหว่างเอนทิตีให้เหมาะสม
## โครงงานฐานข้อมูล 3DPrinter-Store

### 4.1 วัตถุประสงค์
การออกแบบความสัมพันธ์มีเป้าหมายเพื่อลดข้อมูลซ้ำซ้อน รักษาความถูกต้องของข้อมูลที่เชื่อมโยงกัน รองรับการซื้อขาย และเก็บประวัติคำสั่งซื้อได้แม้ว่าสินค้าจะถูกลบออกจากฐานข้อมูลอย่างถาวร เอกสารนี้อธิบายแนวทางที่ใช้ในระบบปัจจุบัน **ไม่ได้สั่งให้แก้ไขโครงสร้างฐานข้อมูลที่ใช้งานได้แล้ว**

### 4.2 การปรับความสัมพันธ์แบบหลายต่อหลาย (M:N)
**คำสั่งซื้อและสินค้า:** หนึ่งคำสั่งซื้อมีสินค้าได้หลายรายการ และสินค้าหนึ่งรายการปรากฏในหลายคำสั่งซื้อได้ จึงใช้ตารางเชื่อม `orderitem` เพื่อแยกเป็น

- `order` **1:N** `orderitem`
- `product` **1:N** `orderitem` (การอ้างอิงสินค้าสามารถเป็นค่าว่างได้หลังจากลบสินค้า)
- `orderitem` เก็บ `order_id`, `product_id`, `quantity`, `price_at_purchase`, `product_name_at_purchase` และ `sku_at_purchase`

**ตะกร้าสินค้าและสินค้า:** ตะกร้าหนึ่งใบเก็บสินค้าได้หลายรายการ และสินค้าหนึ่งรายการอยู่ในตะกร้าของผู้ใช้หลายคนได้ จึงใช้ตารางเชื่อม `cartitem` เพื่อแยกเป็น

- `cart` **1:N** `cartitem`
- `product` **1:N** `cartitem`
- `cartitem` เก็บรหัสตะกร้า รหัสสินค้า และจำนวนที่เลือก โดยมีข้อกำหนด UNIQUE ที่ `(cart_id, product_id)` เพื่อไม่ให้สินค้าเดียวกันแยกเป็นหลายบรรทัดในตะกร้าเดียวกัน

### 4.3 การแยกข้อมูลอ้างอิง
แยก `brand` และ `category` เป็นเอนทิตีต่างหาก และเชื่อมกับ `product` ผ่าน `brand_id` และ `category_id` เพื่อหลีกเลี่ยงการเก็บชื่อยี่ห้อหรือชื่อหมวดหมู่ซ้ำในทุกแถวของสินค้า รวมถึงช่วยให้จัดการชื่อได้สอดคล้องกัน ทั้งสองคอลัมน์อาจเป็น `NULL` ได้ตามโครงสร้างตารางสินค้าที่ตรวจสอบแล้ว

### 4.4 การเก็บรักษาประวัติการซื้อ
ตาราง `order` เก็บผู้สั่งซื้อ วันเวลา ที่อยู่จัดส่ง สถานะ และยอดรวม (`total_amount`) ส่วน `orderitem` เก็บจำนวนและราคาขณะซื้อ (`price_at_purchase`) ไม่ใช่ราคาปัจจุบันของสินค้า

คอลัมน์ `product_name_at_purchase` และ `sku_at_purchase` เป็น **ข้อมูลบันทึก ณ เวลาซื้อ (snapshot)** ที่ตั้งใจจัดเก็บไว้ แม้จะมีข้อมูลบางส่วนซ้ำกับตารางสินค้า เพื่อคงข้อมูลรายการที่ลูกค้าซื้อจริงเมื่อสินค้าถูกเปลี่ยนชื่อหรือลบออกในภายหลัง จึงเป็นการเก็บซ้ำเพื่อรักษาประวัติ ไม่ใช่ความซ้ำซ้อนที่เกิดจากการออกแบบผิดพลาด

ความสัมพันธ์ `orderitem.product_id` อนุญาตค่า `NULL` และกำหนด **`ON DELETE SET NULL`** เมื่อสินค้าถูกลบ รายการซื้อยังคงอยู่พร้อมข้อมูล snapshot ส่วน `cartitem.product_id` ใช้ **`ON DELETE CASCADE`** เพื่อนำสินค้าที่ถูกลบออกจากตะกร้าโดยอัตโนมัติ ทั้งนี้การลบสินค้าต้องไม่ทำให้คำสั่งซื้อและประวัติรายการซื้อหายไป

### 4.5 การแยกผู้ใช้ ตะกร้า และคำสั่งซื้อ
`user` เก็บบัญชีผู้ใช้ `cart` เก็บรายการที่ผู้ใช้กำลังเลือก ส่วน `order` เก็บธุรกรรมเมื่อทำการสั่งซื้อ การแยกตารางช่วยไม่ให้รายการในตะกร้าที่เปลี่ยนแปลงได้ปะปนกับประวัติการสั่งซื้อที่ต้องเก็บรักษา สำหรับจำนวนตะกร้าสูงสุดต่อผู้ใช้ ควรตรวจสอบข้อกำหนดของ `cart.user_id` ในฐานข้อมูลจริงก่อนระบุว่าเป็นความสัมพันธ์แบบ 1:1 อย่างเคร่งครัด

### 4.6 การทำ Normalization
- **รูปแบบปกติที่ 1 (1NF):** แยกรายการสินค้าแต่ละรายการเป็นแถวใน `cartitem` หรือ `orderitem` ไม่เก็บรายชื่อสินค้าหลายรายการในคอลัมน์เดียว
- **รูปแบบปกติที่ 2 (2NF):** คุณลักษณะของตะกร้าและคำสั่งซื้ออยู่ในตารางหลัก ส่วนจำนวนสินค้าและราคาที่ซื้ออยู่ในตารางรายการที่เกี่ยวข้อง
- **รูปแบบปกติที่ 3 (3NF):** แยกข้อมูลยี่ห้อและหมวดหมู่เป็นตารางอ้างอิง ไม่เก็บชื่อดังกล่าวซ้ำในตารางสินค้า
- **ข้อยกเว้นโดยตั้งใจ:** เก็บชื่อสินค้า SKU ราคาขณะซื้อ ที่อยู่จัดส่ง และยอดรวม ณ เวลาทำธุรกรรมเพื่อให้ประวัติสะท้อนข้อมูลจริง โดยไม่คำนวณย้อนจากข้อมูลสินค้าปัจจุบันที่เปลี่ยนแปลงได้

การอธิบายข้างต้นเป็นการวิเคราะห์แนวทางออกแบบ หากต้องการยืนยันว่าทุกแอตทริบิวต์ผ่าน 3NF อย่างสมบูรณ์ จำเป็นต้องตรวจสอบ functional dependency และข้อกำหนดเพิ่มเติม

### 4.7 การรักษาความถูกต้องของข้อมูล
- ใช้ Primary Key เพื่อระบุแต่ละแถว และใช้ `product.sku` ที่ไม่ซ้ำกัน
- ใช้ Foreign Key ควบคุมการอ้างอิง พร้อมกำหนดพฤติกรรมเมื่อลบข้อมูลตามความเหมาะสม
- ใช้ข้อกำหนด CHECK ป้องกันราคาติดลบและจำนวนในรายการซื้อที่ไม่เป็นบวก
- การบันทึกคำสั่งซื้อและปรับสต็อกควรอยู่ใน Transaction เดียวกันเพื่อป้องกันข้อมูลค้างบางส่วน
- การซ่อนสินค้า (`is_active = 0`) ไม่ลบข้อมูลสินค้า ส่วนการลบถาวรจะลบข้อมูลสินค้าโดยยังรักษารายการประวัติซื้อไว้

### 4.8 สรุป
ฐานข้อมูลใช้ตารางเชื่อมสองตาราง แยกข้อมูลอ้างอิงยี่ห้อและหมวดหมู่ แยกตะกร้าจากคำสั่งซื้อ และกำหนดกฎการลบที่สอดคล้องกับธุรกิจ ทำให้ระบบจัดการสินค้า รองรับการสั่งซื้อ และเก็บรักษาประวัติได้อย่างเหมาะสม
